KPI Engine & Agent

01Overview

The repository is two packages with a hard boundary between them. kpi_engine is the deterministic core: it detects material KPI movements, attributes them to drivers, and emits structured evidence. No LLM appears anywhere inside it — that's deliberate. kpi_agent is the LangGraph layer on top. It calls a model exactly twice — once to turn a plain-language question into a validated pipeline configuration, once to write prose — and never to produce a quantity. Everything between those two calls is kpi_engine, untouched.

The engine runs as one stage chain, each stage independently runnable via its own CLI script, or all at once through pipeline.run_pipeline:

profile→ panel→ EDA→ detect→ window→ attribute→ evidence→ evaluate
exactalgebra over the KPI's own definition — Shapley, LMDI. Sums to the total, no assumptions.
estimatedquasi-experimental methods on an upstream driver — DiD, ITS, DML. Never presented as exact.
llm-touchedchooses the analysis configuration or writes prose. Never computes a number.

05kpi_engine.profiling

Finds duplicate columns and linear identities before anything downstream can treat collinear columns as independent causal drivers.

Buckets by rounded sum/std/count, then pairwise-diffs within a bucket. Tolerance 1e-6.

Brute-force ±1-coefficient search over combinations up to 3 terms — catches things like Total Gross Profit = Net Sales − COGS.
resolve_redundancy(column_order, duplicate_groups, identities) -> (groups, dict[str,str])
An identity over k columns drops exactly one, never k.
measure_coverage(df, date_column, grains) -> list[GrainCoverage]

Entry point — chains all of the above.

08kpi_engine.detection

STL → expanding baseline → {point, changepoint, multivariate} → event windows.

Deliberate, not a bug

Detection's STL period is not grain-aware, unlike EDA's. Setting period=4 at weekly grain was measured: flags 96→73, events 11→8, recall 100%→83.3%. A 4-period cycle at weekly grain lets STL absorb a month-long shock as seasonality.

decompose.py
decompose_series(series, spec) -> DecompositionResult
STL wrapper, with a flat fallback when there isn't enough data.
baseline.py
fit_expanding_baseline(values, spec, period=7, refit_every=7) -> BaselineResult
Ridge or seasonal-naive. Strictly no lookahead — trains only on data before t.
robust_scale(residual, mad_floor=1e-9) -> (median, MAD)
point.py / changepoint.py / multivariate.py
detect_point_anomalies(...) -> list[Flag]
Modified z-score via robust_scale.
detect_changepoints(...) -> list[Flag]
PELT and/or CUSUM per spec.method.
detect_multivariate(residuals, periods, support, entity, spec) -> list[Flag]
Mahalanobis distance, shrunk covariance, chi-square cutoff.
windowing.py
build_event_windows(flags, panel, contract, spec, profile, ...) -> list[EventWindow]
Entry point. Clusters flags by entity; an event needs ≥2 flags from ≥2 detector families and ≥1 material deviation — that gate raised precision 42.9%→54.5% at unchanged 100% recall.
runner.py
run_detection(panel, spec, contract) -> DetectionOutput
Entry point — drives point/changepoint/multivariate per KPI×entity.

11kpi_engine.pipeline

The whole chain in one process, returning objects rather than argv-chaining CLIs. What kpi_agent calls.

run_pipeline(spec, contract, detection, *, run_id, graph=None, eda=None, dataset=None, kpis=None, entity_keys=None, time_grain=None, date_range=None, report_window=None, top_events=None, telemetry=None, write_artefacts=True) -> PipelineResult
Chains: load → profile → panel → [eda] → detect → window → [attribute if graph given]. Writes kpi_panel.parquet, flags.json, events.json, series_profiles.json, evidence_bundles.json, run_manifest.json under outputs/<run_id>/.
date_range vs. report_window

date_range restricts what is read, and therefore starves the baseline. report_window detects over the full history and filters events at the end. Loading only "last quarter" gives the detector 3 periods against a 28-period requirement — it finds nothing and reports a quiet quarter, a wrong answer that looks right. kpi_agent always uses report_window.

13How kpi_agent is wired

The agent takes a plain-language question and both data sources, profiles them, turns the question into a validated pipeline configuration, runs the deterministic engine, and narrates the result — grounded by construction. The narrator's entire context is a numbered fact table derived from evidence bundles; it cannot reach the panel, the raw frame, or anything the engine didn't emit as evidence.

Grounding is enforced, not requested

kpi_agent/verify.py is a deterministic, mechanical check — no second model adjudicating the first. The prompt asks the narrator to quote only from the fact table; the verifier checks that it did. Two failed passes drop to a template that renders the same numbers with no model involved. The floor under the whole design is: the worst case is a terse true report, never a fluent false one.

15The LLM layer

One file configures the model; nothing wraps the call. kpi_agent/llm.py holds the constants and the constructor — intent.py and narrate.py call .with_structured_output(...).invoke(...) on the model object themselves, directly, in the node.

constantvaluemeaning
DEFAULT_MODELgemini-3.5-flash-litethe only place a model name is written; --model overrides per run
TIMEOUT_SECONDS150per-attempt deadline
ATTEMPTS3worst case ≈ 7.5 min for one call
MAX_OUTPUT_TOKENS16000shared cap — the narrator's payload is the larger of the two
REASONING_EFFORTmediumpassed to Gemini's reasoning_effort

build_llm(model=None) → ChatGoogleGenerativeAI

The single constructor. Loads .env, builds one langchain_google_genai.ChatGoogleGenerativeAI. Built once per run and shared by both call sites — both take the same effort and output cap, which is what makes a single shared object correct. temperature is deliberately never set: the Gemini 3 family samples at fixed settings and warns if sent one, and every quantity in a report is fixed by the fact table regardless of decoding.

Why not a client wrapper class

An earlier version wrapped the call in a GeminiClient.parse(...) method. It's gone: the nodes now call LangChain's own .with_structured_output(schema, method="json_schema", include_raw=True).invoke(messages) directly. method="json_schema" sends the Pydantic model's own model_json_schema() as response_json_schema — $ref, anyOf, and the additionalProperties: false that extra="forbid" emits all survive the trip, and the reply is validated against that same strict model on the way back. A fabricated field is refused twice over, with no dialect-translation layer to maintain.

The two call sites

callwhereschema outeffort
#1 — planintent.plan_intentAnalysisIntentmedium
#2 — narratenarrate.narrateNarrativemedium

Message order is fixed at both sites: a frozen system prompt, then the stable context block (catalog / evidence), then the varying user turn last. Gemini's context caching is an implicit prefix match with no handle to manage, so that ordering is the entire optimization.

Usage & the --no-llm path

Usage (a dataclass in llm.py) accumulates calls, tokens_in, tokens_out, cache_read from LangChain's normalized usage_metadata — input tokens already include cache reads, output tokens already include thinking tokens, so nothing is double-counted. .cost_usd is None when a model's rates aren't supplied — an unpriced model reports token counts and declines to state a dollar figure rather than reporting a fabricated $0.00.

run_agent(..., llm=None, ...) is the entire --no-llm path: both plan_intent and narrate graph nodes check for llm is None and take the deterministic branch — default_intent and fallback_narrative respectively. No API key is touched.

The top-level entry point. Puts llm and a fresh Usage() into the config dict, invokes the compiled graph with recursion_limit=40. DEFAULT_CONFIG wires two sources (retail_daily, scm_weekly) at time_grain="week", entity_keys=["Region"], top_events=5.
